# --- PDF sources (pdf_derive.py, and ocr.py's PDF-rasterization fallback) ---
# Google's PDFium, for rasterising a PDF's pages. Chosen over the
# alternatives on licensing and packaging: BSD/Apache with self-contained
# wheels, so no system dependency to install (unlike pdf2image's poppler)
# and no AGPL obligation on the app that links it (unlike PyMuPDF).
pypdfium2>=5.13.0

# --- OCR only (ocr.py) ---
# Pinned exactly, and this is not housekeeping - leaving these open cost a
# real, large regression. `ocr.py` names the *detector* model but let the
# recognizer default, and paddleocr 3.7.0 introduced PP-OCRv6 and re-routed
# every Latin-script language from `latin_PP-OCRv5_mobile_rec` to the far
# heavier `PP-OCRv6_medium_rec` (paddleocr/_pipelines/ocr.py, _PPOCRV6_LANGS).
# Nothing in this repo changed - `git log` shows ocr.py's engine setup is
# byte-identical to the initial commit - but a fresh `pip install` silently
# swapped the model underneath it and OCR got dramatically slower.
#
# ocr.py now pins every model name explicitly, so this can't recur silently;
# these pins are the second line of defence. Re-verify with
# py/tools/bench_ocr.py before raising any of them.
#
# Second thing to re-check on a bump: paddlepaddle 3.3.1 cannot run the text
# *detector* under oneDNN - it raises `ConvertPirAttribute2RuntimeAttribute`
# from the PIR executor. `ocr.py` works around that by registering the
# detector in PaddleX's own MKLDNN_BLOCKLIST, so oneDNN can stay on for the
# recogniser, which is ~95% of the runtime and where the speed is. If a newer
# paddlepaddle fixes the detector, that workaround can go and detection gets
# faster too. It reaches into a private PaddleX module path, so a PaddleX bump
# is the other thing that can break it - it fails soft (back to today's
# speed), but check the log line. See docs/OCR-PERFORMANCE.md.
paddleocr==3.7.0
paddlepaddle==3.3.1
numpy==2.3.5
opencv-python==5.0.0.93
