# NBCG-DC — Code Structure & Team Ownership

> Status: proposal (for team review)
> Last updated: 2026-07-28

How the single Vue + Tauri executable is laid out so the three of us can work in
parallel with minimal collisions. The guiding rule: **separate by layer, and let
the layer boundaries fall on file-type boundaries**, so nobody has to edit a file
that mixes concerns (no Python-in-TypeScript, no API-service-in-markup).

## Roles → lanes

| Developer | Focus | Lane | File types |
|-----------|-------|------|-----------|
| **Jernej** | backend connection, user flow, functionality — the glue that runs everything | Application / logic | `.ts` (services, stores, composables, IPC, domain, router) |
| **GUI dev** | the interface, look & feel | Presentation | `.vue`, `.css` (views, components, design tokens) |
| **Arch/DevOps dev** | Rust core, Python scripts, packaging & CI | Native + Ops | `.rs`, `.py`, CI/config |

The layer boundaries are drawn so each lane is, in practice, a single file family:
**Presentation is `.vue`/`.css`, Application is `.ts`, Native is `.rs`/`.py`.** A
GUI file never contains an API call; an API service never contains markup; no file
mixes Python and TypeScript.

## The three lanes

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  PRESENTATION              APPLICATION / LOGIC              NATIVE + OPS        │
│  GUI dev                   Jernej                           Arch/DevOps dev     │
│  .vue · .css               .ts                              .rs · .py · CI      │
│                                                                                 │
│  views/  components/  ──▶  composables/  stores/  ──▶  ipc/  ══invoke══▶  src-tauri/  ──spawn──▶  py/
│  design/                   services/  domain/  app/     (typed bridge)    (Rust core)          (Python)
│                                       │                                                            │
│                                       └────── services/api ═══HTTP═══▶  nbcg backend              │
└──────────────────────────────────────────────────────────────────────────────┘
     seam 1: composables        seam 2: IPC contract        seam 3: REST      seam 4: Python CLI
     (GUI ↔ Jernej)             (Jernej ↔ Arch)             (Jernej only)     (Arch internal)
```

Data flows **down**: presentation binds application state; the application layer
reaches the OS through the typed IPC bridge and the backend through the REST
client; the native core drives the Python scripts. Nothing flows back up across a
lane except through a documented seam.

## The four seams

The only places two lanes meet. Keep them thin and documented and the lanes stay
independent.

### Seam 1 — Presentation ↔ Application (GUI dev ↔ Jernej)
**Contract: composables.** A `.vue` file imports a `useXxx()` composable and binds
its reactive state + action methods. Presentation files **never** import from
`services/`, `api/`, `ipc/`, or `stores/` directly — only from `composables/`,
other `components/`, and `domain/` (types only).

- GUI dev works against a documented composable interface, not the backend.
- Result: no `.vue` file ever contains an API/IPC call; no service ever contains
  markup.

### Seam 2 — Application ↔ Native (Jernej ↔ Arch dev)
**Contract: the IPC command + event surface.** The single source of truth is the
Rust command signatures + `dto.rs` types. **`tauri-specta` generates
`src/ipc/bindings.ts`**, so the bridge is typed end-to-end and any change on the
Rust side surfaces as a TypeScript compile error.

- Jernej calls `ipc.jobs.start(batchId)`; Arch implements `#[tauri::command] fn
  jobs_start(...)`.
- No file mixes the two: `services/pipeline.ts` is TS, `commands/jobs.rs` is Rust.

### Seam 3 — Application ↔ Backend (Jernej only)
**Contract: the REST API** (see [09 – Backend API contract](tasks/09-backend-api-contract.md)).
Lives entirely in `services/api/` as TypeScript, using
`@tauri-apps/plugin-http`. DTO types in `services/api/dto.ts`, ideally generated
from the backend's OpenAPI. The Arch dev is not involved here — all backend
connection is in Jernej's lane.

> **Decision — backend HTTP is in TypeScript, not Rust.** This keeps every
> backend-connection concern in Jernej's lane and out of the Rust core. Trade-off:
> the static Keycloak token passes through the webview (acceptable — it already
> lives in app config). If the token must never leave Rust, expose a single
> `ipc.backend.request()` command instead — but that moves backend code into the
> Arch lane, which we don't want. Revisit only if security requires it.

### Seam 4 — Native ↔ Python (Arch dev, internal)
**Contract: the Python CLI** — arguments in → output files + a JSON summary on
stdout + exit codes, documented in `py/README.md`. Both sides are owned by the
Arch dev, so this seam never crosses a role boundary; `commands`/`core/python`
(Rust) is the only caller.

## Making the boundaries mechanical

Convention alone drifts. Enforce the lanes in the repo:

- **`CODEOWNERS`** mapping each folder to its owner's GitHub handle, so every PR
  auto-requests the right reviewer and ownership is unambiguous.
- **`eslint-plugin-boundaries`** (or `import/no-restricted-paths`) that **fails the
  build** if a `.vue` imports a service, or a service imports a component. Suggested
  layers: `presentation` (`views`, `components`, `design`) → may import
  `composables`, `domain`; `application` (`stores`, `composables`, `services`,
  `ipc`, `app`) → may import `domain`, each other; `presentation` may **not** import
  `services`/`ipc`/`stores`.
- **Path aliases** in `tsconfig.json` + `vite.config.ts`
  (`@domain @services @ipc @stores @composables @ui @lib`) so imports read cleanly
  and any cross-lane import is obvious in review.
- **`tauri-specta`** for the Rust → TS type bridge (seam 2), so the IPC contract is
  single-sourced.

## Getting started per lane

- **GUI dev:** build against stub composables that return mock view-models; no
  backend or Rust needed to develop and style the whole UI.
- **Jernej:** own `domain/` first (the shared types both other lanes consume), then
  the IPC contract and API client; wire stores/composables to feed the UI.
- **Arch/DevOps dev:** stand up the `commands/` surface + `core/` modules behind it
  and the Python invocation strategy (open question — see
  [03 – decisions](03-open-questions.md)); the typed bindings flow to Jernej via
  tauri-specta.
